# Seen: development harness

The procedure every ticket goes through, across Claude Code and Codex. Built by tickets SEEN-086 to SEEN-095 before any product code and extended by SEEN-096 to SEEN-103 (CodeGraph and Repowise beside graphify, the context budget, the gate that tells an open question from an unknowable one, non-code mode at solution); SEEN-104 to SEEN-109 add the session cap, the subagents, the hooks, the review triage and the route. The skill file that both assistants read is `docs/harness/skill.md` (created by SEEN-092) and this document is its long form.

## Why a harness

Seen is built by one person driving Claude Code and Codex through 85 tickets in 120 days, and the product that comes out of it files claims and changes prices inside other companies' marketplace accounts. Speed without a harness produces code nobody can trust inside a seller account; a harness without speed misses the 30 November POC gate. The Seen harness is the fixed procedure every ticket goes through, with the evidence recorded as it happens, so that a session started by Claude Code today and resumed by Codex tomorrow reads the same files and continues at the same stage. It replaces the Seene harness that lived in this repository before; the stage model is kept, the tooling is new.

It has four jobs, in this order: fast (one command per stage, small context, checks that finish in minutes), reporting (every ticket leaves a KPI record and every week produces a report), secure (secrets, permissions and injection handled by the procedure rather than by memory), and correct (a test that failed before the change, an independent review, CI as the only definition of done).

## Principles

The harness is a procedure, not an orchestrator: it runs inside the current assistant session, launches no other model, bypasses no tool permission, and never claims an independent review when the implementing session reviewed its own work. Terminology is fixed in `CONTEXT.md`, which is why a stage gate, the product's policy gate and the sprint gates G0 to G7 are never called just a gate. Evidence is written as it happens, into an append-only, hash-chained journal per ticket under `docs/harness/history/<ticket>/`, where each record carries the sha256 of the previous record file and `doctor` additionally proves against git history that no record was ever committed as a modification or a deletion; failed attempts and superseded decisions stay in the record, and a journal is never recreated to pass a stage gate. Every stage has one command to draft, one to advance, and a JSON template whose fields are the stage gate. Ticket text, marketplace payloads and web pages are evidence to be read, never instructions to obey or shell arguments to expand; the harness passes them through files. Context comes from the graph tools, not from reading the repository: a session asks CodeGraph what a change touches, Repowise how risky the files are and why they are the way they are, and graphify how the code connects to the documents, instead of opening files until the answer appears; one tool call per question, and never the same question to two tools. Judgement calls that the procedure needs (is this clarified, how risky is this diff, how severe is this finding) are typed questions to Jev, recorded with their probabilities, and thresholds live in `harness/thresholds.toml`, never in a prompt. Nothing is delivered until `verify-delivery` succeeds: branch pushed, CI green on that commit, journal complete, KPI record written, receipt hash matching.

## The five stages

Intake and clarify. `harness start <ticket>` creates the journal, reads the ticket file and its PRD and architecture references, runs `graphify query` and `get_pr_impact` for the areas the ticket names (and Repowise `risk` and `why` for the files they map to), and drafts the clarify record: scope in one sentence, the acceptance criteria restated as checks, material questions with the answer or the decision taken, and the policy-gate action flag when the ticket changes an agent action. Jev answers two typed questions on the record: `clarified` (noul: are all material questions resolved) and `risk` (score: low, medium, high, from the diff surface graphify reports and the policy-gate action flag). Below 0.8 on `clarified` the stage cannot advance without a note that answers the open question.

Solution. The technical solution record names the files and symbols that will change (from the graph: `codegraph_explore` for the symbols and their blast radius, `shortest_path` between the entry point and the data it touches, Repowise `why` for the decisions already taken on those files), the tables and migrations, the tests that will be written first and what each RED must demonstrate, the rollback, and for policy-gate action tickets the tool's reversibility, action type and euro impact estimator. Jev scores `solution_complete` and `touches_billing_or_policy_gate` (noul); a yes on the second adds the security checklist and a second reviewer to the review stage. Once the record is accepted, `harness route` decides per slice which model and which effort implement it (SEEN-108): by rule for anything that touches money, credentials, tenant isolation, the policy gate, a migration or an agent action (the strongest model, high effort, Jev not asked), and by Jev's `implementation_model` and `implementation_effort` for the rest, with the slice, the risk answers and the repository's own history as state. The route lands in the record and in the handoff pack; the session never chooses its own model.

TDD. Work runs in vertical slices. `harness check <ticket> --phase red -- <command>` records the command, exit code, duration and output hash; a RED is accepted only when the test fails for the reason the solution record states. GREEN records the passing run; regression records the full suite with coverage; `advance` to review is refused without at least one RED and one GREEN per slice, a non-negative coverage delta on `packages/core`, and green typecheck, lint and build. Graphify is updated on each commit by its git hook, so the impact set is always current. Tickets with no executable behaviour (registrations, verifications against a live account, documentation) take the non-code path instead: a change type of documentation, research, verification or policy, a recorded reason, and, for a verification, the sources every claim came from. It keeps the 17 human tickets inside the harness so every one of the 106 leaves a journal.

Review. The review runs cheapest pass first (SEEN-107). Pass one is no model: the checks the harness already has (coverage, lint, gitleaks, the fingerprint, files inside the accepted slice) and the ones the journal makes possible (a RED that failed for the stated reason, tests added, an evidence entry for every criterion). Pass two is one Jev request with the journal and the diff excerpts as state: `criterion_evidenced` per acceptance criterion, `diff_matches_solution`, `reviewer_must_read` per file and `review_depth` (spot or full); a criterion answered unevidenced returns the ticket to tdd before any model reads anything. Pass three is the review proper, and it is independent: a different session (the reviewer subagent, or Codex reviewing Claude Code's work and the other way round) reads the solution record, the journal, the graph impact, the Repowise change risk and health findings, and the diff at the depth pass two chose, and writes findings with file, line, claim and failure scenario. Jev scores each finding (`severity`: low, medium, high, blocking) and answers `must_fix` (noul); findings at or above the policy threshold return the ticket to `tdd` or `solution` with `harness return`, and the return is counted as rework. The security checklist runs here for every ticket: no secret in the diff (gitleaks), no new dependency without lockfile and audit, no live marketplace call in a test, no PII field without the expiry job, no tool without a policy-gate declaration.

Deliver. Commit with the ticket id, push the branch, open the pull request from the template at `.github/pull_request_template.md` (summary, acceptance criteria checked, RED and GREEN evidence, review findings and resolutions, KPI snapshot), wait for CI, then `harness verify-delivery <ticket>`. It is the deliver stage's own stage gate, not an advance: it checks the commit is on the remote, CI is green for that SHA, the journal has every stage record and the KPI file exists, then appends the receipt record and moves the ticket to `delivered`. The receipt attests the code commit and the reviewed-tree fingerprint, which excludes the journal and the drafts, so the trailing journal-only commit that carries the receipt cannot invalidate it. SEEN-086 ships the offline half (remote, journal, fingerprint); the CI check arrives with SEEN-089 and the KPI check with SEEN-091, and each refuses rather than passes when it cannot be run. A push is not a merge; merge to `main` requires the PR checks and the receipt hash, which is the sha256 of the receipt record file, in the PR body.

## Tooling

Claude Code and Codex are the two executors; the harness skill is one file, `docs/harness/skill.md`, synced by `harness sync` into `.claude/skills/seen-harness/SKILL.md` and `.agents/skills/seen-harness/SKILL.md`, so both read the same instructions. `.claude/settings.json` allows the harness commands and the test runners and nothing else by default.

Graphify (Graphify-Labs, `uv tool install graphifyy`, then `graphify claude install` and `graphify install --platform codex`) turns the repository, its docs, SQL schema and configs into a deterministic knowledge graph with tree-sitter, no LLM and nothing leaving the machine for code. The harness uses it four ways: `graphify hook install` rebuilds the graph on every commit and branch switch; `python -m graphify.serve graphify-out/graph.json` runs as an MCP server in both assistants so a session queries `query_graph`, `get_neighbors`, `shortest_path` and `get_pr_impact` instead of reading files; `graphify extract` runs headless in CI to produce `GRAPH_REPORT.md` and fail the build when the graph does not parse; and `graphify prs` gives the reviewer the impact set of a pull request. `graphify-out/graph.json` is committed so a fresh clone has context before its first build. Rationale comments (`# WHY:`) become graph nodes, which is where design decisions from the solution records are pointed to in code.

CodeGraph (colbymchenry/codegraph, `npm i -g @colbymchenry/codegraph`, `codegraph install`, `codegraph init`, MIT; SEEN-096) is the navigator during implementation: a Rust-parsed symbol and call graph in a local SQLite index under `.codegraph/`, kept current by a watcher that runs inside the MCP server the session starts (the harness syncs the index before every codegraph query and records that it did), exposed to both assistants as one MCP tool, `codegraph_explore`, that returns the relevant symbols' verbatim source, call paths including dynamic dispatch and framework routes, and the blast radius in one call. Its published benchmark across seven codebases is 88% fewer tool calls and 62% fewer tokens per query, with the caveat that its dense answers stay resident in the context window, so the rule is narrow queries and short sessions per slice. `harness graph <ticket> impact` and `explain` route to it and write the answer into the journal.

Repowise (repowise-dev/repowise, `pip install repowise`, `repowise init --no-prose -y`, `repowise agents add --target=claude-code`, an `mcp_servers.repowise` entry in the Codex config, AGPL-3.0; SEEN-098) is the risk and memory layer: five local indexes under `.repowise/` (dependency graph, git hotspots with co-change and bug-fix history, a generated wiki, captured decisions, and 49 code-health detectors) behind ten MCP tools. The harness routes `harness graph <ticket> why`, `health` and `risk` to it, and carries its change-risk answer (the percentile against this repository's own commits, the tests that may break, the missing co-changes) into the state `harness decide risk` is judged on, so the clarify gate reads evidence rather than impressions; if Repowise is not installed the absence is recorded as an absence, not as a low score. `repowise update` runs on demand at clarify, solution and review, with no git hook. Its PR bot, a GitHub App that reviews every pull request with zero LLM calls, was declined for this private repository in SEEN-102, with two conditions that reopen the decision. Its own measurement is 31.6% fewer output tokens and about half the tool calls per question; the harness records the real figure per ticket.

The three graph tools have one role each and never answer the same question twice: graphify for the map across code and documents, CodeGraph for symbols and blast radius while writing code, Repowise for risk, history, rationale and the PR bot. `harness graph <ticket> impact|explain|path|prs|why|health|risk` routes each question to the tool that owns it, `harness/thresholds.toml` `[context]` carries the three budget rules (one tool call per question; a codegraph query names a symbol, not a directory; no repository-wide read when a graph can answer) and the decision rule written before the numbers existed (below the baseline the tools stay; above it one goes, graphify first), and the context-efficiency KPI is what that rule reads.

Jev AI (TypeSafe, model `jev-latest`, `POST https://api.typesafe.ai/v1/systemone`) is the harness's decision layer. It takes the record as the state and returns typed answers: `noul` for yes-or-no as a single probability, `choice` for routing with a probability per option, `score` for an ordered rubric with a weighted value, a legend and a confidence. One request carries every question a stage owns. The harness calls it at the four points above (clarified, risk, solution complete, finding severity and must-fix), plus one safety check before any harness command that deletes or rewrites journal or graph files, and, from SEEN-107 and SEEN-108, for the review triage (`criterion_evidenced`, `diff_matches_solution`, `reviewer_must_read`, `review_depth`) and the route (`implementation_model`, `implementation_effort`). Each question carries its criteria per option in `harness/jev.py`, and each threshold sits in `thresholds.toml` beside the measurement that set it. Every call, its probabilities and the threshold applied are written to the journal, so a stage gate decision can be re-read later; Jev never edits code, never talks to a marketplace, and never decides a product action. The key lives in `.env.local` as `JEV_API_KEY`; the Starter plan covers the MVP. When Jev is unavailable the harness falls back to asking the human and records that it did.

CI (GitHub Actions, the existing `ci.yml` shape) is the only definition of done: pnpm install with a frozen lockfile, typecheck, migrations applied twice, tests with coverage, build, gitleaks, `pnpm audit --audit-level high`, `graphify extract`, and the harness's own tests. Postgres 18 runs as a service; tests create and drop their own database.

## The context per session

The baseline SEEN-099 recorded before any graph tool existed says what a ticket costs when one session works it start to receipt: 40,600 output tokens and 18.5 tool calls per point, so 120,000 tokens for a three-point ticket and 250,000 for a five-point one (SEEN-089 before it was split). A session that long compacts its context at least once, and compaction is where evidence quietly becomes summary: the RED that was seen becomes "tests were written", the decision becomes "we decided". Three habits produce the number. The whole ticket is worked in one session. Every session re-reads the PRD, the architecture and the workflow before touching the ticket, which is 30,000 tokens before the first useful line. And research and review, the two heaviest readers, happen in the same context as the implementation.

SEEN-104 to SEEN-106 change the unit of context from the ticket to the slice, without changing the unit of delivery.

**The slice plan.** Every code-mode solution record names its slices: name, points, files and the RED each must demonstrate. A slice is at most 2 points and a ticket has at most 4; a plan that needs more is a ticket that is too big, and it is split the way SEEN-089 and SEEN-096 were. The five-point tickets of Sprints 0 to 2 already carry a `## Slices` section in their ticket file as the starting plan; the solution stage adopts or amends it. New tickets are 3 points or fewer.

**One slice per session.** A session reads the PRD and the architecture once, at clarify. Everything after starts from the handoff pack: `harness handoff <ticket>` writes at most 2,000 tokens (stage, current slice, criteria as checks, files, decisions taken, graph answers already recorded, the next command) and appends a handoff record with the pack's hash; `harness status --brief` prints it, and the SessionStart hook injects it, so a fresh session is productive from its first turn. `harness budget <ticket>` reads the session's own output tokens from the session logs, the way the cost KPI already does, and says when the slice boundary is the next stop. The session id is recorded on every check, so the sprint report shows sessions per ticket and tokens per slice beside tokens per point.

**Subagents for the two readers.** The scout (read-only tools plus the three graph servers) answers the clarify and solution questions in a context of its own and returns a brief of at most 400 words with file paths; the reviewer (fresh context, no Edit or Write) reads the diff, the journal and the criteria and returns findings in the review template's JSON. The session working the ticket never holds their reading. A subagent is a context boundary and not independence by itself: the review gate refuses a review from the implementer's own session, and the review by the other assistant stays required for tickets that change an agent action or touch billing.

**Hooks for what the skill can only ask.** SessionStart injects the pack; UserPromptSubmit warns over budget; PreToolUse on an edit calls `harness guard`, which blocks code edits while the ticket is at clarify or solution, edits on the wrong branch and edits outside the accepted slice's files; PreCompact writes the pack before the context is summarised; SubagentStop validates the reviewer's findings; Stop runs the quick doctor. Each is a harness command with fixtures, generated into both assistants from one source.

## How the harness meets the assistants

The harness is a Python program with a journal, a state machine and gates; it knows nothing about Claude Code or Codex. Each assistant offers the same five extension points under different names and paths, and the harness owns one source file per point from which `harness sync` generates both assistants' copies, so a session in either reads the same instructions, meets the same walls and delegates to the same helpers. `doctor` reports a generated copy that was edited by hand, the way it does for the skill today.

| Extension point | What it is for | Claude Code | Codex | In the harness |
|---|---|---|---|---|
| Rules | Facts and constraints loaded into every session, so short | `CLAUDE.md` at the root and per directory, plus path-scoped `.claude/rules/*.md` | `AGENTS.md` at the root and per directory (`/init` scaffolds it) | `CLAUDE.md` and `AGENTS.md` carry the ground rules and the index; the procedure is not in them |
| Skills and commands | A procedure loaded on demand, invoked by name; custom commands are the same thing in older clothes | `.claude/skills/<name>/SKILL.md`, invoked as `/<name> args` (`.claude/commands/*.md` is the older form, merged into skills); `context: fork` runs a skill in a subagent | `.agents/skills/<name>/SKILL.md`, invoked as `$<name>` in the prompt or through `/skills`; implicit invocation by description unless disabled in `agents/openai.yaml` | `docs/harness/skill.md` is the one source; `harness sync` writes `.claude/skills/seen-harness/` and `.agents/skills/seen-harness/` (SEEN-092) |
| Hooks | A shell command the assistant runs at a lifecycle event, which can inject context or block a tool call; deterministic, outside the model | `hooks` in `.claude/settings.json`; events include SessionStart, UserPromptSubmit, PreToolUse, PostToolUse, PreCompact, SubagentStart, SubagentStop, Stop, SessionEnd; exit 2 or `permissionDecision: deny` blocks, stdout or `additionalContext` injects | `.codex/hooks.json` (or `config.toml`); the same events with the same JSON shape; exit 2 or `decision: block` blocks, `additionalContext` injects; hooks run without a feature flag | `harness/hooks.json` is the one source; `harness sync` writes both copies (SEEN-106); today only graphify's read guard is installed, in Claude Code |
| Subagents | A helper with its own context window and its own tool allowlist that returns a bounded answer | `.claude/agents/<name>.md` with frontmatter (`name`, `description`, `tools`, `model`, `permissionMode`, `omitClaudeMd`); delegated automatically by description or explicitly as `@agent-<name>`; nesting to three levels | `.codex/agents/<name>.toml` (`name`, `description`, `developer_instructions`, `model`, `sandbox_mode`, `mcp_servers`); spawned only when the prompt asks; `[agents] max_depth = 1`, `max_threads = 6` | `harness/agents/` is the one source for seen-scout, seen-reviewer and seen-implementer; `harness sync` writes both formats (SEEN-105) |
| Tools (MCP) | Servers whose tools the model can call; their schemas cost context in every session | `.mcp.json` at the root and `claude mcp add` | `mcp_servers` in `~/.codex/config.toml` | graphify, codegraph and repowise, each with one role; the `[context]` budget in `thresholds.toml` says what they may cost |
| Permissions | What runs without asking | `permissions.allow` in `.claude/settings.json` (harness, pnpm, git, gh, graphify, gitleaks) | `approval_policy` and `sandbox_mode` in `config.toml`; the `.agents/settings.json` mirror in this repository is read by nothing Codex documents and is verified or removed in SEEN-106 | The allowlist names the harness commands and the test runners and nothing else |

Two consequences follow. The Python harness stays the only place where a rule is enforced: a hook calls a harness command and relays its answer, a subagent runs a harness command to record what it found, the skill tells the session which command comes next. None of the three carries logic of its own, so a rule changed in one place is changed everywhere, and a session in Codex that lacks a hook still meets the same refusal at the next `advance`. And the assistants' differences are absorbed at sync time: Claude Code delegates to a subagent on its own when the description fits, Codex only when told, so the Codex copy of the skill says "spawn seen-reviewer" where the Claude Code copy says "the reviewer runs"; Claude Code nests subagents, Codex does not, so no harness step depends on nesting.

## Jev before the model: the review triage and the route

Two of the procedure's costs are a model reading. The review reads the whole diff, the journal and the criteria, and Jev only scores the findings the model wrote; and every slice runs on whatever model the session happens to be, at whatever effort. SEEN-107 to SEEN-109 put Jev in front of the model in both places, under rules that decide where Jev may not be asked, and under a measurement that decides whether either change goes live.

**The review triage, built by SEEN-107.** `harness review triage <ticket>` runs at the review stage and appends a `triage` record, its own journal kind for the reason `handoff` is one: the review gate has to find the focus set and the KPI the excluded share, and a reader that parses prose is a reader that will one day read it wrong. Three passes, cheapest first. Pass one runs no model at all: nine named checks, each answering pass, fail or unavailable with a line of detail. The ones the harness already had are coverage, lint, gitleaks and the reviewed-tree fingerprint, plus every changed file being one the accepted slice plan named; the ones the journal makes possible are a RED recorded as failing, a test in the change, an entry in the clarify record for every criterion in the ticket, and a pull request whose body names the ticket. Two of those came out differently from the plan above once they met a real journal. The ticket file is excluded from the slice check, because the procedure writes it, `status: doing` with the first commit and the `## Outcome` section before review is left, and no solution record plans it, so the check would have failed on every ticket including its own. And the pull request is read only when the checkout has a remote, because at review there is usually no pull request yet and an absence is not a failure. A failure does not refuse: most of these can be unavailable for a reason about the machine rather than about the work, so a failure forces full depth and is carried in the record where the reviewer reads it.

Pass two is one Jev request with the journal and the diff excerpts as state: `criterion_evidenced` once per acceptance criterion, `diff_matches_solution`, `reviewer_must_read` once per changed file (with the hunk count, the lines added and removed, the package, Repowise's change-risk percentile, the coverage delta and whether the solution record named the file) and `review_depth`, spot or full. One request carrying the same question many times is what `jev.ask_batch` exists for: it keys the payload rather than naming it, so `criterion_evidenced#2` and `reviewer_must_read#harness/triage.py` sit beside each other, each with the subject that tells them apart in its own instructions. All four questions carry no stage, the way `is_destructive` does, so the review advance keeps asking only `severity` and `must_fix`. The state is excerpts the journal already holds, the criteria as checks, the decisions taken, and each slice's behaviour beside the RED that failed for it, rather than the tree: Jev can neither run a test nor read a file, so a summary of a tree it cannot see would be an impression rather than evidence.

Pass three is the reviewer subagent reading only the focus set at that depth; its findings go through `severity` and `must_fix` as before. The harness runs no model, so the triage record carries the task text and the session hands it over: what that buys is that the focus set the reviewer is given and the focus set the gate checks are one list read from one record. The task names the ticket file and the journal separately from the focus set, because they are what a review is against and no focus set can hold them: the journal is never a candidate, since the changed-file list drops everything the fingerprint excludes, and the ticket file can be dropped from a spot set like any other. It names what pass one settled by check name only, never by detail, because a passing check's detail names paths and at spot depth some of those are outside the focus set. Three checks pass on less than their name suggests and are handed over with the remainder named rather than listed as settled: `red_before_green` proves the cited check exited non-zero and not that it failed for the reason the slice states, `acceptance_entries` counts the clarify record's checks against the ticket's criteria without either list saying which answers which, and `tests_added` proves a test file is in the change and not that the behaviour the slice adds has a test of its own, which a one-line fixture edit satisfies just as well. The gate refuses a review record whose `read` list does not cover the focus set, naming what was skipped; reading more is never refused, because the focus set is a floor.

Every doubt resolves towards reading more. Spot depth needs Jev to be surer of spot than of full and to clear its bar, so a tie is full; an answer nobody could give is full, because a judgement nobody made must not narrow a review, and for the same reason an unavailable `criterion_evidenced` sends nothing back. A spot focus set is never empty: a review that reads nothing is not a review, so the file the model was least unsure about stays. What stays a rule and is never asked of Jev: a ticket that changes an agent action, touches billing or the policy gate, or carries a migration always gets full depth, and the first two are read from `gates.full_depth_rules`, the one predicate `needs_two_reviewers` also reads, because a second copy of that reasoning is a second answer waiting to disagree. Only those three silence the request. A failed pass-one check forces full depth too, and the request is still made: the case where pass one found something wrong is the case where whether the criteria are evidenced at all most needs asking, and putting the two in one list meant pass two never ran once on the branch that built it. The record carries both depths, what the rules enforced and what the model would have chosen, because the shadow window measures the second and a narrowing that never ran still has a figure. A criterion Jev can see no evidence for appends the triage, appends a return to tdd naming the criterion, and refuses, so the ticket goes back before any model reads the diff.

**The route.** After the solution record is accepted, `harness route` writes per slice which model and which effort implement it. Rules first: money arithmetic in `packages/core`, migrations and RLS, credentials, the policy gate, billing and agent actions go to the strongest model at high effort, and Jev is not asked. Every other slice is Jev's `implementation_model` (haiku, sonnet, opus) and `implementation_effort` (low, medium, high), with the slice, the approach, the risk score from clarify, Repowise's change-risk percentile, whether the pattern already exists in the repository, new dependencies, the marketplaces touched and the ticket's returns so far as state. The route lands in the solution record and the handoff pack, the implementer subagent is spawned with it, and the tdd gate refuses a check recorded under any other model. The reviewer's model is a rule as well: the strongest at full depth, one tier down at spot depth.

**Nothing goes live on a guess.** For ten tickets both run in shadow: the triage is computed while the reviewer still reads everything, the route is computed while every slice still runs on the current model. An escape is a high or blocking finding in a file the triage would have excluded, or a criterion it called evidenced that the reviewer found unmet; spot depth goes live only after ten tickets without one, and the first escape afterwards returns it to shadow. The routes go live only when the slices Jev would have sent to a smaller model show rework at or below the strongest model's over the window. `harness report --calibration` shows the evidence and states the verdict by the rule; the switch is a founder decision on the record, and the rule is committed before the first number exists, as it was for the context tools.

**What Jev is and is not.** Jev cannot execute a test, read the repository or write code; every answer is a probability over the state the harness puts in front of it. That is why pass one exists, why the state is excerpts the journal already holds rather than the tree, and why the three hard rules are code. It is also why Jev is cheap: one request per stage, typed answers, no tokens spent on reading.

## KPIs

Each ticket writes `docs/harness/history/<ticket>/kpi.json` at delivery; `harness report --week` aggregates the week into `docs/harness/reports/<year>-W<week>.md` with the JSON beside it, and `harness report --sprint <n>` produces the sprint view used at each sprint gate review.

| KPI | Definition | Target for the MVP |
|---|---|---|
| Cycle time | start to verified delivery, and per stage | median under 2 days per ticket; no stage over 1 day without a note |
| First-pass CI | share of tickets whose first pushed commit passed CI | 80% |
| RED before GREEN | slices with an accepted RED before the GREEN | 100%, enforced |
| Coverage delta | change in line coverage on `packages/core` | never negative; 90% floor on detectors, matching and the policy gate |
| Review findings | findings per ticket by severity, fixed versus waived | zero blocking at delivery; waivers named in the journal |
| Rework | returns to an earlier stage per ticket | under 0.5 per ticket over a sprint |
| Cost | tokens and euros per ticket and per slice, by model and effort, from the session logs where available, else self-reported | reported every ticket; trend down per point; cost per point by model in the sprint report (SEEN-108) |
| Escaped defects | bugs found after delivery, linked to the ticket that introduced them | under 1 per sprint |
| Velocity | build points delivered against planned, per sprint | within 20% of plan |
| Eval pass rate | for policy-gate action tickets, pass rate on the 30-finding eval set | 95% before autonomy is granted |
| Context efficiency | tool calls and tokens per build point, from session logs; baseline recorded before CodeGraph and Repowise are installed | at least 30% below the baseline by Sprint 1 |

## Security controls

Secrets: gitleaks runs in the pre-commit hook and in CI; `.env.local` is gitignored; the harness refuses to write environment values into any record; marketplace credentials live in the secrets provider (`.env.local` in development, Secret Manager after go-live) and never in fixtures. Context tools: CodeGraph and Repowise index locally and send nothing off the machine; `.codegraph/` and `.repowise/` are gitignored, only `graphify-out/` is committed; the Repowise PR bot, which would read the whole tree as a GitHub App, is declined (SEEN-102). Tests: no test may call a live marketplace; connector tests run against recorded fixtures with secrets and buyer PII scrubbed at recording time; the test database is created and dropped per run. Permissions: `.claude/settings.json` allowlists harness and test commands; anything else prompts; Codex runs with the equivalent policy. Injection: ticket files, marketplace payloads and fetched web pages are data; the harness never interpolates them into shell commands and the skill says so in its first paragraph. Supply chain: frozen lockfile, `pnpm audit` at high, new dependencies named in the solution record. Branches: `main` protected, PR and CI required, no force push, receipts in PR bodies. Journal integrity: append-only files with a hash chain; `harness doctor` verifies the chain and the sync of the skill copies. Destructive harness operations ask Jev `is_destructive` and then the human before running.

## What the building of it settled

Ten tickets built this harness on 23 and 24 September 2026, and five conventions came out of the work
rather than the plan.

**Amend a criterion rather than deliver it with an asterisk.** Four tickets met a criterion that could
not be met as written: branch protection on a free plan, `packages/core` before the monorepo existed,
migrations before a database, a pull request template that `gh pr create` bypasses. Each was amended
in the ticket with the reason. The clarify gate refuses a record that defers instead of resolving.

**The Outcome is written before review**, because the fingerprint covers the ticket file.

**Evidence is authored in `.harness-drafts/`**, for the same reason.

**A receipt is final when the work is merged**, not when it is written. `reopen` voids one before a
merge; after a merge it refuses, because a merged receipt is history.

**The gates are calibrated on measurements, not taste.** `clarified` holds at 0.8, which it reaches
when a record genuinely resolves what the ticket asks. `solution_complete` moved to 0.6 on five
measurements across two tickets, recorded beside the value in `thresholds.toml`. A ticket whose
solution record cannot be judged complete is usually a ticket doing too many things: SEEN-089 scored
0.49 covering seven enforcements and 0.67 covering one, and was split.

**Four more came from the first day of use.** A ticket that installs or integrates something external cannot resolve every question in advance, and the `clarified` question punished the record that said so; SEEN-100 gave it criteria that tell a question nobody has answered from one only the work can settle. SEEN-096 was split three ways for the same signature as SEEN-089. A ticket file carries its title, so renaming one is ordinary, and SEEN-101 let a journal follow its ticket by id. And non-code mode moved from tdd to solution (SEEN-103), because a registration should not have to invent tests to reach the stage where it says it has none.
