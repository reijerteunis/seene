## Description

Implement the Postmark inbound webhook in apps/api: parse forwarded mail, strip signatures and quoted text, identify the marketplace and the order or case id with per-marketplace patterns (Bol first, since it has no messaging API), attach the mail to an existing thread or claim or open a new thread, and store attachments as evidence. Unmatched mail lands in an ops queue rather than being dropped.

How a Message-ID is stored is settled by SEEN-008 and is not a choice here. The trade record schema classifies `messages.external_message_id` and `message_threads.external_thread_id` as not buyer PII on the condition that this ticket stores a digest of the Message-ID and never the id itself. On the four marketplace rails the id is the rail's own and holds nothing about anybody; on mail it was generated by the sender's system, which on an inbound message is the buyer's, so it carries their sending host to the right of the at sign and a local part their client chose. Stored raw it is buyer data in a column SEEN-083's 30-day expiry never visits, because that job reads the classification and the classification says it is not. A digest still recognises a message the mailbox delivers twice and still resolves an In-Reply-To onto the message it answers, which is the whole of what threading needs. The reason is set out in full in the column comments of `supabase/migrations/20260929000002_trade_record_v1_free_text_classification.sql`, SEEN-008's second review recorded the promise living nowhere this ticket's author would read it as F34, and `packages/core/db/schema.test.ts` goes red if the criterion below leaves this ticket.

## Acceptance criteria

- [ ] A forwarded Bol customer question is matched to its order and thread by order id in a fixture set of 50 mails with at least 90% matched
- [ ] A Bol compensation confirmation mail attaches to the claim as a claim_event
- [ ] Attachments are stored in the evidence store with sha256
- [ ] Unmatched mail appears in the ops console queue with a reason
- [ ] A Message-ID is stored as a digest and never as itself in messages.external_message_id or message_threads.external_thread_id, proved by a fixture mail whose raw Message-ID appears in no column of the trade record
